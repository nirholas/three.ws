# Access control and least privilege policy

Owner and approver: the platform owner. Review cadence: every 12 months and whenever a service account or role changes. Last reviewed: 2026-11-16. Approval: pending the owner's signature.

## Rules

1. One identity per person and per workload. Humans use their own Google accounts; workloads use dedicated service accounts. No shared human logins.
2. Roles are the narrowest that work. The inventory below is regenerated by `npm run compliance:m365-evidence` (file `iam-service-account-bindings.json`) and compared with this table at each review.
3. Multi-factor authentication is required for every human interface that can change production: the Google account that owns the Cloud project, the GitHub account that owns the repository, and the application's admin surface (enforced in code: [api/_lib/admin-mfa.js](../../api/_lib/admin-mfa.js), a session without a verified second factor gets `403 mfa_required`; sessions idle for 60 minutes are ended). The owner confirms the first two in each annual review; the application rule is verified by `tests/` for admin-mfa and by the evidence run.
4. Service account keys are avoided. Where a user-managed key still exists it is listed in the risk register with a removal date.
5. Access is removed the same day it stops being needed. Accounts unused for three months are reviewed in the quarterly pass below.

## Service accounts

| Account | Used by | Roles (project level) |
|---|---|---|
| `three-ws@` | the Cloud Run runtime | `aiplatform.user`, `artifactregistry.reader`, `cloudtrace.agent`, `logging.logWriter` |
| `three-ws-build@` | Cloud Build and deploys | `cloudbuild.builds.builder`, `run.admin`, `secretmanager.secretAccessor`, object admin on the backup bucket |
| `three-ws-autopilot@` | the unattended maintenance VM | `aiplatform.user`, `cloudbuild.builds.editor`, `cloudscheduler.admin`, `logging.viewer`, `logging.logWriter`, `run.admin`, CDN invalidate |
| `three-ws-domains@` | domain and DNS automation | `dns.admin`, `domains.admin` and one custom domain-connect role |

Human project owners: three accounts hold `roles/owner` (listed in `iam-owner-editor-bindings.json` of each evidence run). The default compute service agent holds `roles/editor`, which is Google's default for the Cloud Services agent.

## Database and data access

- The database is reachable only with the connection string held in Secret Manager (`database-url`, `database-url-unpooled`), readable by the runtime and build accounts. Human access is by the owner through the Neon console.
- The list of people with access to data or encryption keys is, today, the owner only. It is re-confirmed in the annual review and written into the review log of the [information security policy](information-security-policy.md#review-log).
- Application roles for customers (team owner and fixed-ceiling roles) are enforced server side and documented on [/trust#access](https://three.ws/trust#access). Every admin and team admin action is written to the audit log with IP and user agent.

## Quarterly access review

Every quarter the owner runs `npm run compliance:m365-evidence`, reads `iam-service-account-bindings.json`, `iam-owner-editor-bindings.json`, `service-account-user-managed-keys.json` and `admin-users-mfa.json`, removes anything not justified by the table above, and records the date. Findings from 2026-11-16 are in the risk register (R3).
