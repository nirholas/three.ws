# Knowledge rerank eval, 2026-11-16

Does the NVIDIA hosted cross-encoder in [api/_lib/rerank.js](../../../api/_lib/rerank.js) make knowledge retrieval better, and what does it cost in latency? Short answer: the model is excellent (nDCG@5 1.000 against 0.860 for cosine), but hosted queue latency is too high and too variable for the interactive chat path, so the stage stays **opt-in** (`KNOWLEDGE_RERANK_ENABLED=1`).

## Step 0: which rerankers are alive

Every hosted reranker has its own URL, `https://ai.api.nvidia.com/v1/retrieval/<publisher>/<model>/reranking`, and `GET /v1/models` never lists rerankers, so each candidate was probed directly with our `NVIDIA_API_KEY` on 2026-11-16 (one query, two passages).

| Model | HTTP | Response |
|---|---|---|
| `nvidia/nemotron-3.5-rerank-8b` | 200 | `{rankings:[{index, logit}], usage}`, 4.7 s cold |
| `nvidia/llama-nemotron-rerank-vl-1b-v2` | 410 | Gone, end of life 2026-11-16 |
| `nvidia/llama-nemotron-rerank-1b-v2` | 410 | Gone, end of life 2026-08-25 |
| `nvidia/llama-3.2-nv-rerankqa-1b-v2` | 410 | Gone, end of life 2026-05-18 |
| `nvidia/llama-3.2-nemoretriever-500m-rerank-v2` | 410 | Gone, end of life 2026-05-18 |
| `nvidia/rerank-qa-mistral-4b` (previous pin) | 404 | function not found for account |
| `nvidia/nv-rerankqa-mistral-4b-v3` | 404 | function not found for account |

The URL path keeps the dot in `3.5`; the underscored slug (`nemotron-3_5-rerank-8b`) answers 404. Pinned: `nvidia/nemotron-3.5-rerank-8b` (`DEFAULT_RERANK_MODEL`, override with `KNOWLEDGE_RERANK_MODEL`).

Four retirements in six months, each arriving silently as 404/410, is why the stage now has a retirement guard (below).

## Method

- **Corpus.** Every 12th top-level `docs/*.md` in sorted order at commit `64b05444c`, kept when 2 KB to 60 KB, chunked with the production chunker (`api/_lib/knowledge-chunker.js`, kind `docx`): 652 chunks from 49 docs. The corpus is rebuilt from that commit at run time, so later doc edits never move the labels.
- **Labels.** 48 hand-written questions in [data/evals/rerank/questions.json](../../../data/evals/rerank/questions.json). Each was written by reading one chunk and paraphrasing what it answers without reusing its heading or wording; `relevant` names that chunk. Every other chunk is a distractor.
- **Pipeline.** The production one: embed with `nvidia/nemotron-3-embed-1b@2048`, take the cosine top 12 (`SEARCH_POOL`), reorder that pool with the real `rerankPassages()`. Chat injects the first 4 (`CHAT_TOP_K`).
- **Metrics.** nDCG@5, hit@1, hit@4 (what chat sees), hit@5. Each query is reranked twice and **every call is scored on its own**, because production makes one call per retrieval: a call that fails serves the cosine order, and its wall time still counts as added latency.
- **Runner.** [scripts/nvidia-rerank-eval.mjs](../../../scripts/nvidia-rerank-eval.mjs). Raw output: [results-2026-11-16-t2500.json](../../../data/evals/rerank/results-2026-11-16-t2500.json), [results-2026-11-16-t20000.json](../../../data/evals/rerank/results-2026-11-16-t20000.json).

All 48 answer chunks were inside the cosine pool, so the reranker always had the right passage to promote.

## Results

| | Cosine | Rerank, 20 s timeout | Rerank, 2.5 s timeout (production) |
|---|---|---|---|
| nDCG@5 | 0.860 | **1.000** (+0.140) | 0.889 (+0.029) |
| hit@1 | 0.750 | **1.000** (+0.250) | 0.802 (+0.052) |
| hit@4 (chat) | 0.938 | **1.000** (+0.062) | 0.948 (+0.010) |
| hit@5 | 0.958 | **1.000** (+0.042) | 0.969 (+0.011) |
| Calls answered | | 96 / 96 | 21 / 96 |
| Added latency p50 / p95 / max, all calls | | 2049 / 5199 / 11626 ms | 2502 / 2504 / 2506 ms |
| Latency p50 / p95, answered calls | | 2049 / 5199 ms | 1633 / 2410 ms |
| Calls that needed the hedge | | 54 | 77 |

On every query where cosine missed the top slot (12 of 48, gold at cosine ranks 2 to 8), the reranker put the answer first. On the 16 queries where at least one call answered inside 2.5 s, it scored a perfect 1.000 nDCG@5 against 0.825 for cosine on those same queries. The quality is there; the latency is not.

Latency is queue-dominated, not compute-dominated: the same 29-token request measured 0.5 s, 2.6 s and 4.6 s back to back, and an earlier run of this eval the same day had a p50 of 2.3 s against 4.5 s for a later one. A hedged second request (fired after 1 s, or at once when the first fails with 5xx/429/network) trims the tail but cannot fix a queue that is slow for every request.

## Content-safety screening

The hosted endpoint screens every passage and rejects the **whole batch** with `422 {"error":{"message":"input rejected by content safety screening"}}` if any one passage is flagged. On this corpus that hit 7 of 48 queries (r04, r07, r14, r35, r36, r41, r43), caused by 9 ordinary doc chunks (OData usage docs, timeout utilities, embedding docs, a transaction race write-up). Before the fix those queries silently fell back to cosine.

Pair logits do not depend on the batch, so on a safety 422 the stage now scores each passage alone, in parallel, and merges: scored passages are ordered by logit exactly as the batch would have ordered them, and each flagged passage keeps its cosine slot, so the reranker neither promotes nor buries what it could not read. A safety 422 is never treated as a retirement. With the split in place, the 20 s run answered 96 of 96 calls (14 of them through the split path).

## Decision

**Rule:** enable by default only when, at the production timeout, the served nDCG@5 gain is at least **+0.05** and the added p95 over all calls is at most **1500 ms**.

| Timeout | Served nDCG@5 gain | Added p95 | Verdict |
|---|---|---|---|
| 2500 ms | +0.029 | 2504 ms | fails both |
| 20000 ms | +0.140 | 5199 ms | fails latency |

No timeout clears both halves: a timeout short enough for the latency budget leaves most calls unanswered, and a timeout long enough to answer them adds seconds to every chat turn. The stage therefore stays **opt-in**. An owner who prefers quality over latency for a particular deployment sets `KNOWLEDGE_RERANK_ENABLED=1`; it is then bounded by a hard 2.5 s timeout (`RERANK_TIMEOUT_MS`), hedged, and fails open to the cosine order on any error.

Re-run the eval before flipping the default, for example if NVIDIA's hosted queue improves or a self-hosted reranker NIM lands on our GPU fleet (which removes the shared queue entirely):

```bash
NVIDIA_API_KEY=... node scripts/nvidia-rerank-eval.mjs run --repeat 2 --timeout 2500
```

## Retirement guard

On 404 or 410 the stage disables itself for 6 hours (`RETIRED_COOLDOWN_S`) in this process and in the shared cache, records the event exactly once across instances (`cacheSetIfAbsent` on `rerank:retired:<model>`), and pages ops through `sendOpsAlert` with signature `rerank:model-retired:<model>`. Until the cool-down lapses every retrieval skips the network call, so a retired model costs zero latency. Re-pin with `KNOWLEDGE_RERANK_MODEL` (a config-only `gcloud run services update --update-env-vars`) after probing a replacement as in step 0.

Tests: [tests/rerank.test.js](../../../tests/rerank.test.js) (reordering, fail-open on 5xx/429/network/non-JSON/partial rankings, the hard timeout, the safety split, hedging, retirement alert-once, shared-cache flag, re-pin bypass, cool-down expiry).
