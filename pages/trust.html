Hosting and regions

The API and website run as one container on Google Cloud Run (service three-ws-api, region us-central1, Iowa, United States), deployed by Cloud Build under dedicated build and runtime service accounts. Scheduled jobs run on Cloud Scheduler. Cache and rate-limit state live in Memorystore for Redis on a private network that is not reachable from the internet.

The database is Neon managed PostgreSQL in AWS us-west-2 (Oregon). User files are stored in Cloudflare R2. All customer data is processed in the United States. We do not offer data residency in other regions today.

Encryption

In transit

HTTPS only, with Strict-Transport-Security: max-age=63072000; includeSubDomains; preload on every response. Calls to the database, object storage and model providers use TLS. The Redis link runs over Google's private network.

At rest

Each storage provider encrypts data at rest by default: Google Cloud, Neon and Cloudflare R2. On top of that, the application encrypts its most sensitive values itself:

  • Custodial wallet keys and per-agent provider keys: AES-256-GCM with HKDF-derived keys and a random nonce per record, under a key separate from the session secret.
  • Sessions, OAuth refresh tokens and API keys: stored only as SHA-256 hashes. The raw value is shown once and never stored.
  • Passwords: bcrypt.

Authentication

  • People: email and password, Sign-In With Solana, EVM wallet sign-in (EIP-4361, single-use nonces), Google, GitHub and X, or Privy social sign-in. Browser sessions are opaque 32-byte random tokens in a __Host- cookie (HttpOnly, Secure, SameSite=Lax) with a 30-day lifetime.
  • Apps and MCP clients: OAuth 2.1 with PKCE, where only S256 is accepted, and audience-bound access tokens that expire after one hour. Refresh tokens rotate, and if an old one is reused the whole token chain is revoked. Scoped API keys can be revoked at any time.
  • Microsoft Marketplace buyers sign in with their Microsoft Entra ID work account to activate a purchase.
  • Enterprise SSO: SAML 2.0 service-provider support is built and can be enabled for a deployment with that organisation's identity provider. It is not enabled on three.ws today.
  • Multi-factor: three.ws has no built-in second factor today. Wallet sign-in is passwordless, and SSO sign-in inherits the identity provider's MFA policy. Passkeys are not supported yet.

Access control and admin access

Every API request is checked against the caller's scopes. Records belong to the user or agent that owns them, and generated files stay private to their owner until the owner publishes them. Agent skills declare the permissions they need, and the user grants them.

Admin endpoints require a signed-in session whose wallet is on a short allowlist or whose account is flagged as an admin in the database. Production infrastructure is reached through Google Cloud IAM, and secrets are held in Google Secret Manager rather than in the repository.

Logging and monitoring

Request and error logs go to Google Cloud Logging. Every server fault and every reported browser error becomes an alert, deduplicated by signature. Critical alerts reach the operator by private Telegram chat and email immediately; warnings arrive in an hourly digest. A probe checks the platform, API and payment surfaces every 5 minutes and publishes the results on the status page. Signer keys are scanned for leaks every 15 minutes.

Chat message content is not logged. Security audit logs are kept for 365 days.

Backups and recovery

The database runs on Neon, which keeps a history of changes so it can be restored to an earlier point in time within the plan's restore window. Audit records, older usage records and pruned market-feed data are archived to Google Cloud Storage and checked against the source before any row is deleted. Every deploy is an immutable Cloud Run revision, so a bad release can be rolled back in one command.

We do not yet run scheduled database dumps to storage outside Neon. The last full dump was taken by hand on 8 July 2026, and automating it is in progress.

Wallet custody

Every agent gets a custodial Solana wallet: three.ws holds the key, encrypted as described above, so the agent can act without a person approving each transaction. That means we hold signing power, and we say so plainly. The controls on it:

  • Owner-set spend limits (daily and per transaction) and a destination allowlist, enforced on the server before anything is signed.
  • A one-tap freeze that stops all autonomous spending but never blocks the owner's own withdrawal.
  • A custody event trail of every withdrawal, spend, limit change and freeze, with balances committed to a Merkle attestation that anyone can re-verify in the browser.
  • Social recovery and inheritance that transfer ownership of a wallet without exposing its key.

Wallets people connect themselves from their own browser or mobile wallet app are never custodial. Their keys never reach three.ws.

AI data use

three.ws does not train models on your prompts, files or photos. Most 3D generation runs on our own GPU workers in Google Cloud, so that content does not go to a third party. Chat goes to hosted model providers in a failover order. Free lanes come first, which means a prompt can reach any provider in the order below. The terms each provider publishes for its API:

ProviderUsed forWhat the provider publishes
GroqDefault chat lane"By default, Groq does not retain customer data for inference requests." Inputs and outputs may be logged for up to 30 days for reliability and abuse investigation. Source
OpenRouterChat failover, free models"Wherever possible, OpenRouter works with providers to ensure that prompts will not be trained on, but there are exceptions." Some downstream providers "may train on it if marked." Source
NVIDIAChat failover, speech recognition, text-to-3DNVIDIA's API catalog documentation makes no statement about training on or retaining submitted inputs. We treat it as a provider that may retain them. Privacy policy
OpenAIPaid chat backstop, embeddings"Data sent to the OpenAI API is not used to train or improve OpenAI models." Abuse-monitoring logs are "retained for up to 30 days." Source
Google Vertex AIGemini chat anchor, Imagen images"Google won't use your data to train or fine-tune any AI/ML models without your prior permission or instruction." Cached data is "deleted no later than 24 hours after it's written." Source
Cloudflare Workers AIImage understanding"Cloudflare does not use Customer Content processed by Workers AI to train AI models." Source

Because free lanes lead the order, do not put confidential or personal data in prompts. Selfie photos for avatars go to our own reconstruction service. We never use them for training and never derive a face template from them.

Incident response and status

Incidents are detected automatically, as described under logging. Responders can contain one by rotating a secret, freezing wallets, revoking sessions, rolling back to an earlier revision, or turning off a feature with its kill switch. If a breach affects personal data, we notify affected users, and regulators where the law requires, without undue delay and within the legal deadline, for example 72 hours under GDPR. Live availability is on the status page.

Vulnerability disclosure

Report vulnerabilities privately to security@three.ws. We aim to acknowledge reports within 48 hours and to ship fixes for critical issues within 7 days. Please give us a reasonable window to fix an issue before disclosing it publicly. Do not access other people's data, disrupt the service, or move funds you do not own while testing.
