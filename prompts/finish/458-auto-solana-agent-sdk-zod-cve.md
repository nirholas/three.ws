## Why this matters (measured 2026-10-25)

1. **The advisory, from GitHub's own API (not a secondary paraphrase):** `curl https://api.github.com/advisories/GHSA-mrhx-c7xc-m3w5` returns severity `high`, CVSS 7.5 (`AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H`), `vulnerable_version_range: "< 4.6.6"`, `first_patched_version: "4.6.6"`. Full description: "Zod schema-validation library through 4.6.5 contains an uncontrolled resource consumption vulnerability that allows attackers to exhaust memory by submitting a large array to an application using an array schema without a length constraint. Attackers can exploit the handleArrayResult parse logic in `$ZodArray`, which accumulates every validation issue for each failing element with no cap or early termination, causing the process to allocate excessive issue objects and crash due to out-of-memory conditions." Note the advisory's own technical detail (`$ZodArray`, `handleArrayResult`) names zod v4's internal class/function, not v3's differently-structured parser; the npm range `< 4.6.6` is a mechanical semver cutoff that also happens to span all of v3.x. Task 1 below requires you to check whether v3.25.76's actual source has the same unbounded-issue-accumulation behavior before treating "unreachable in our schemas" as the only mitigating fact; don't rely on the range field alone to decide severity.
2. **Where it lives in this repo:** root `package.json` pins `"zod": "^4.6.7"` (lines 58, 774; safe, already past the patched version). The nested workspace package `solana-agent-sdk/package.json` declares `"zod": "^3.0.0"` twice, once as an optional `peerDependency` (lines 64-70) and once as a `devDependency` (line 79, used to run its own Jest suite). `node -e "console.log(require('./package-lock.json').packages['solana-agent-sdk/node_modules/zod'].version)"` resolves this to `3.25.76`, inside the vulnerable range, in a nested `node_modules/zod` that root's safe `^4.6.7` pin does not and cannot override (it's a separate resolution tree).
3. **How it got there:** the single most recent commit on `main` at measurement time, `1ad300d5b` ("fix(deps): add the zod 3.25.76 lock entry that npm 11.9.0 in Cloud Build requires"), added this exact lockfile entry for an unrelated reason: Cloud Build's `npm ci` under npm 11.9.0 rejected the lockfile with "Missing: zod@3.25.76 from lock file" while npm 11.19.1 accepted it; the lockfile was regenerated under 11.9.0 to match. That commit did not introduce the vulnerable version choice (`^3.0.0` in `solana-agent-sdk/package.json` already existed), it just made the lockfile internally consistent again under the older npm Cloud Build runs. Fixing this order's root cause (bumping the `^3.0.0` ranges) removes the need for that specific pin entirely, but you must re-verify the exact Cloud Build constraint that motivated `1ad300d5b` still holds after your change (see Task 3).
4. **Reachability from live production:** `grep -rl "solana-agent-sdk\|@three-ws/solana-agent" api/ --include="*.js"` finds real, deployed route handlers importing the SDK: `api/agenc/[action].js`, `api/agora/act.js`, `api/agora/[action].js`, `api/_lib/agora-human.js`, `api/x402/vanity-verifiable.js`, `api/_lib/service-catalog/services/vanity-verifiable.js`. These are live, request-handling endpoints, not build tooling.
5. **Narrower schema-usage check, already run:** `grep -n "z\.\w\+(" solana-agent-sdk/src/solana-agent-kit/actions.ts` shows only `z.object`, `z.string`, `z.number` (with `.describe()`, `.max()`, `.min()`, `.int()`, `.positive()`, `.optional()` modifiers); no `z.array`, `z.record`, `z.map`, or `z.set` anywhere in `solana-agent-sdk/src/`. `types.ts`'s only zod import is `import type { z }`, a type-only reference with no runtime parsing. This means the specific "oversized array with no length cap" exploit path described in the advisory is not reachable through solana-agent-sdk's own schema definitions as they stand today, pending Task 1's deeper check of whether v3's own array parser has an equivalent flaw.
6. **Why the fix is cheap regardless of the reachability answer:** every zod builder actually used (`z.object`, `z.string`, `z.number`, `.max`, `.min`, `.int`, `.positive`, `.optional`, `.describe`) is stable, unchanged API across the v3 to v4 major bump. There is no need to choose between "migrate" and "document as accepted risk": bumping `solana-agent-sdk`'s zod ranges to match root's already-safe `^4.6.7` is the correct fix either way, and is a small, low-risk change given this usage surface.
