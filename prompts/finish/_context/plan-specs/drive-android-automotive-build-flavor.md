## Why this matters

three.ws Drive puts the agent in the car. `/drive` (web), native CarPlay (Swift, written, waiting on Apple's entitlement) and the Android Auto car app (compiled) exist. Android Automotive OS (AAOS) runs the app on the head unit itself, which covers Polestar, Volvo, GM and others with no phone projection. The car-app templates are identical; only the packaging differs, and the docs list phase 6 as "scoped, not started". The Android Auto overlay explicitly leaves it out (`build.gradle.fragment` comment, `docs/ANDROID-AUTO.md` "Android Automotive OS is a separate build").

## Current state (measured by the reviewer on 2026-11-03)

- Overlay sources: `solana-mobile/android-overlay/app/src/main/java/ws/three/app/drive/{DriveCarAppService,DriveSession,DriveScreen,DriveLink,DriveWebService}.java`, descriptor `res/xml/drive_automotive_app_desc.xml` (this is the Android Auto `<uses name="template"/>` file, despite its name), strings `res/values/drive.xml`.
- `solana-mobile/android-overlay/build.gradle.fragment` has `androidx.car.app:app:1.4.0` and `app-projected:1.4.0`; no `app-automotive`, no `CarAppActivity`, no product flavor.
- The generated Android project is owned by Bubblewrap and regenerated by `solana-mobile/scripts/build-apk.sh`; native code only survives through `solana-mobile/scripts/apply-overlay.mjs`.
- Web half: `src/drive/*`, `pages/drive.html`, `tests/drive-surface.test.js`. `?surface=androidauto` turns the 3D stage and confirmation card off; AAOS needs its own surface decision (a head unit has a display the web view may be attached to).
- Distribution of an AAOS app needs Google's car app quality review plus a Play listing (owner step, outside this order).

## Tasks

1. Decide and document the packaging in `solana-mobile/docs/ANDROID-AUTO.md` (new section "Android Automotive OS"): an `automotive` product flavor that adds `androidx.car.app:app-automotive`, a `CarAppActivity` entry declared with `<uses-feature android:name="android.hardware.type.automotive"/>`, the AAOS `automotive_app_desc.xml` (`<uses name="template"/>`), and `distractionOptimized` metadata only where the Play policy allows it for the declared category.
2. Extend `solana-mobile/scripts/apply-overlay.mjs` and the overlay layout so the automotive flavor is added to the generated Gradle project idempotently (re-running leaves a single copy), without changing the existing phone/Android Auto build output. Add a script test (`tests/` or the script's own `--check` mode) that applies the overlay to a throwaway generated tree and asserts the flavor, dependency and manifest entries exist exactly once.
3. Implement `DriveAutomotiveActivity`/`CarAppActivity` wiring so the same `DriveSession` and `DriveScreen` templates render on the head unit, reusing `DriveLink` and the identical page protocol (`window.threeWsDrive.command`, `ThreeWsDriveNative`). A head unit has no phone to hold the microphone, so confirm the web view lifecycle: the web view stays detached, `?surface=androidauto` (or a new `?surface=aaos` preset added in `src/drive/surface.js`) keeps the 3D stage off, and the confirmation card stays refused while moving.
4. If a new `surface` value is added, extend `src/drive/surface.js` and `tests/drive-surface.test.js` first (test-first), including the phrases the command matcher must not match.
5. Compile it: build the automotive flavor with the Bubblewrap/Gradle path in `ANDROID-AUTO.md` ("Building and running it"). Record the exact command and the result. If the Android SDK or JDK is absent, install them per the playbook in the Never-blocked table and still compile; a flavor that has never compiled is not done.
6. Exercise it on Google's Android Automotive emulator image if the SDK manager can fetch it; otherwise state plainly in the doc that on-device behavior is unverified and what to run.
7. Update `docs/carplay.md` phase 6 row to its real state, add a `data/changelog.json` entry, and add the new files to `solana-mobile/android-overlay/README.md`'s table.

## Definition of done

- [ ] `./gradlew assembleAutomotiveDebug` (or the flavor task name documented) succeeds from the generated project after `apply-overlay.mjs`; the build log tail is in the report.
- [ ] Running `apply-overlay.mjs` twice yields the same tree (the idempotence test passes).
- [ ] The existing phone build task (`assembleDebug` without the flavor) still succeeds and its manifest is unchanged.
- [ ] `npx vitest run tests/drive-surface.test.js` passes with any new surface preset covered.
- [ ] `docs/carplay.md` phase 6 reads accurately; nothing claims on-car verification that did not happen.

## Never blocked

| No Automotive emulator image | Compile and run the unit/idempotence tests, and document the on-device step precisely. |
| Play listing / car app quality review | Owner action after this order; do not attempt it. |
