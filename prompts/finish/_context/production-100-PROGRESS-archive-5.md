Measured: `gcloud logging read` against `three-ws-api` (project `aerial-vehicle-466722-p5`) for the `TypeError: Failed to fetch` client-error signature: 1 in the last 24h, 941 in the last 30d (order author's 2026-10-24 baseline: 9/24h, 109/7d, 952/30d; the 30d count is still essentially flat, confirming the bug is still live and worth fixing). Sample stack trace confirmed the exact chain: `window.fetch` -> `kd.load`/`G_.load` (three-addons chunk) -> `new Promise` -> `G_.loadAsync` -> `picker` chunk -> `z._loadInto` -> `z._buildScene` -> `z.mount` (companion.js), all on `walk-companion.js` auto-injected by `nav.js`'s `initCompanionAutoStart()`.

Resolved the source location without the order's literal sourcemap-build step: read the actual vendored source directly (`node_modules/three/src/loaders/FileLoader.js`, `node_modules/three/examples/jsm/loaders/GLTFLoader.js`) via targeted `node -e` reads, since the minified frame names (`kd`, `G_`) matched FileLoader/GLTFLoader's method shapes exactly and the chunk names (`three-addons`, `picker`) confirmed which vendored module was in play. Root cause: `FileLoader.js` keeps a MODULE-LEVEL (not per-instance) `loading[url]` dedup table; `load()`'s `fetch(req).then()...finally()` chain is never returned or awaited by `load()` itself, and its `.catch()` handler does a bare `throw err` when `loading[url]` is already `undefined` at catch-time, a state that only arises when 2+ callers have registered against the identical URL concurrently. That `throw` has nothing after it but `.finally()` (which does not catch), so it becomes a genuine unhandled rejection no caller-side try/catch can intercept, because it rejects a promise walk-sdk never held a handle to. The V8 async-stack-trace frames (`mount`/`_buildScene`/`_loadInto`) are companion.js's own synchronous call stack at the time FileLoader's internal fetch was created, not evidence that loadAsync()'s own promise (which walk-sdk already try/catches) is the one rejecting.

Did: test-first. Wrote `walk-sdk/test/load-avatar.test.mjs` (new file, 4 cases) against an as-yet-unmodified `load-avatar.js`; ran it and confirmed it failed for the right reason (`does not provide an export named 'coalesceLoad'`, since the guard did not exist yet). Added `coalesceLoad(key, start)` plus `cloneGltfForJoiner(gltf)` to `walk-sdk/src/internal/load-avatar.js`, right after `makeLoader()`: a pure, loader-agnostic in-flight map keyed by URL so a second concurrent request for the same key joins the first caller's promise instead of starting its own `loader.loadAsync()` call, eliminating the only way walk-sdk's own code could ever hand FileLoader two callbacks for one URL. A joined ("non-owner") caller gets a cloned `gltf.scene` rather than the live one, since the existing code mutates and reparents `gltf.scene` directly (`Object3D.add()` steals a child already attached elsewhere), so sharing the live object across two mounts would be unsafe.
