- Root cause, pinned by reading the actual call path: `x-mention-reply.js`'s `chainFor()` gets its chain from `resolveAgentBrain`/`modelChain` (`agent-brain.js` / `agent-model.js`), which both build on `llm-tool-chain.js`'s `providerChain()`, an array of plain `{ name, url, key, model }` records meant to be read directly by `copilot-engine.js`'s own round-trip loop (`runCopilotTurn`, `for (const provider of chain)`, imported straight from `llm-tool-chain.js`). `composePublicReply` instead hands that same array to `llmComplete` (`llm.js`), whose internal attempt loop calls `p.buildBody(system, user, maxTokens)` on every rung, a method only `llm.js`'s OWN `providerChain()` objects define. The two "provider chain" names are different, incompatible shapes used by different callers; `x-mention-reply.js` composed the wrong pairing, so `chainOverride.length` is always truthy (the chain is non-empty, correctly populated, with a real `GROQ_API_KEY` on it) but every attempt throws instantly on the missing method and the whole chain reports "exhausted" in milliseconds. The order's own task 1 wording ("using the provider chain in `llm.js`") describes the correct design; the shipped code used `agent-brain.js`'s chain (the order 044 integration point) instead, by reasonable-looking analogy to the gateway's `chainForAgent`, but that gateway path feeds `runCopilotTurn`, not `llmComplete`, so the shapes never had to match there.
- This is not a corpus artifact: it reproduces for the company account (no agent, exactly what the live mention cron calls) with real production keys, so it reproduces in production too. It also explains evidence order 050's session already captured without knowing why: the live `x_mention_events` table carries 129 rows with `reason: 'fallback:llm_error'` from the real mention-poll cron, recorded before this session touched anything. **The public reply bot has likely never produced a single real model answer to a stranger; it has silently sent the fixed help reply, `FIXED_HELP_REPLY`, every time**, which is safe (the fallback passes every post-check by construction) but defeats the feature's purpose entirely.
- Fix is not attempted here: `x-mention-reply.js` exists only on `main`, this session is scoped to `evolve` and may not edit `main` directly (the harness's own "work only here" boundary, separate from CLAUDE.md), and `main`/`evolve` are already a flagged, unreconciled divergence (row 34, below) that a mechanical single-file fix should not get ahead of. The fix itself is narrow once someone is working on `main`: `chainFor()` should build from `llm.js`'s own `providerChain({ grokKey, grokModel })` (resolving the agent's Grok key/model the same way `agent-grok-key.js`/`agent-brain.js` already do) instead of `modelChain`/`resolveAgentBrain`, so the chain it builds matches what `llmComplete` actually reads.
- Updated `production-100-OWNER-ACTIONS.md` row 34 with this finding so the reconciliation pass fixes it immediately, since it is otherwise invisible (every post-check still passes, nothing errors loudly, and the only trace is the `fallback:llm_error` reason on each row).
- This order's own narrow Definition of Done (tests exist, both suites pass per their own designed pass/fail semantics) is satisfied by what is shipped on `main`, so it retires the same way order 050 did. The deeper defect found while verifying it is tracked in the owner-actions row above, not re-opened as a new order, since the fix lives entirely inside the one function `main` already shipped and needs no new design.
