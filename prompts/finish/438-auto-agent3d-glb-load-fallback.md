## Why this matters (measured 2026-10-25)

Production's Cloudflare R2 bucket is still disabled at the account level:

This is already tracked and owner-gated (`prompts/RUN-ORDER.md` OWNER-ACTIONS row 36). **This order does not touch R2.** It closes a separate, code-fixable gap: when the GLB body fails to load for any reason (this outage, a future one, or a single corrupt/missing object), three client surfaces show the user a dead end instead of recovering, even though the app already ships a local default avatar asset that does not depend on R2 at all.

By contrast, `/u/<username>` pages already degrade gracefully today ("Couldn't load the avatar... You can still chat or open the full walk") and the `/walk` companion widget already falls back client-side to a bundled `robot` asset on a GLB load failure (`walk-sdk/src/internal/load-avatar.js:135-143`, confirmed live via the console warning `[walk] avatar "..." failed to load, falling back to "robot" fetch`), which is immune to the R2 outage because `roster.js`'s `robot` entry (`source: 'static'`, `asset: '/animations/robotexpressive.glb'`) resolves to a same-origin static file, not `/api/avatars/:id/glb`. The three surfaces this order targets have no equivalent.

Root cause, traced to exact lines, not guessed:

1. `src/element.js:1957-1983` (the `<agent-3d>` web component's `boot()`): `uriCandidates(manifest.body?.uri)` only produces more than one candidate for `ipfs://`/`ar://` URIs (gateway fan-out). For the normal case, a plain HTTPS URL such as `https://three.ws/api/avatars/<id>/glb`, it returns an array of exactly one entry (`src/ipfs.js`'s `uriCandidates`, locked in by the existing test `tests/ipfs-uri-candidates.test.js:44-46`, `"returns one entry for a plain URL so callers can loop unconditionally"`). So the retry loop at lines 1966-1981 runs once, throws `bodyErr`, and that propagates straight to `boot()`'s catch block at `src/element.js:2448-2461`, which logs `[agent-3d] boot failed` and calls `this._showError(err)` (`src/element.js:3176-3214`, title `"Couldn't load agent"` for a chat-mode instance, or a quiet decoration fallback with no visible recovery for a bare avatar). There is no fallback to `https://three.ws/avatars/default.glb`, even though that exact URL already exists as the manifest-resolution fallback (`_defaultFallbackManifest()`, `src/element.js:2482-2492`) for a *different* failure (resolving the manifest itself, not loading its body). A body-load failure after a manifest was already resolved successfully never reaches that fallback.
2. `src/avatar-page.js:819-828` (the shared entity-studio controller behind both `/agents/:id` and `/avatars/:id`, per `STRUCTURE.md`'s Entity studio row): the `<model-viewer>` mounted at `src/avatar-page.js:577-603` gets one `error` listener that sets `av-stage-loading`'s text to `'Failed to load 3D model.'` (line 827) and does nothing else. No retry, no fallback `src`, no recovery path.
3. `src/marketplace.js:1636-1667` (`openAvatarModal`, the modal viewer on `/marketplace`): a programmatically created `<model-viewer>` gets an `error` listener (lines 1663-1667) that overwrites the loading label with `'Failed to load 3D model.'` and nothing else; a 15-second timeout (line 1659) separately writes a "try refreshing" message if `load`/`error` never fires at all. Same gap: no fallback `src`.

The fix in all three places follows the pattern already proven live by `/walk`: on a GLB load failure, if the failing URL is not already the local default avatar, swap to the local default avatar GLB (`https://three.ws/avatars/default.glb`, same URL `_defaultFallbackManifest()` already uses, served from `public/avatars/default.glb` which exists on disk and is bundled with the app, not read through `/api/avatars/:id/glb` or R2) and show an honest, recoverable message instead of a dead end. Only if the fallback asset *also* fails does the final "couldn't load" state apply.

This is distinct from and not already covered by any open order: `401` (vitest), `403` (docs freshness), `433` (account_link_codes migration), `435` (sentiment-pulse LKG), `436` (forge-finalize TTL reap) do not touch `element.js`, `avatar-page.js`, or `marketplace.js`. `437` explicitly named this exact gap in its own Never-blocked table as "a candidate for a future, separately-scoped order" and left `api/avatars/[id]/[action].js`'s `handleGlb` untouched on purpose (a server-side image placeholder cannot stand in for a binary 3D model); this order is that future order, and it fixes the problem client-side instead, matching the pattern that already works for `/walk`.
