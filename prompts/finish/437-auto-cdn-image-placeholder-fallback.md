## Why this matters (measured 2026-10-25)

Production's Cloudflare R2 bucket is fully disabled at the account level right now:

    curl -s https://three.ws/api/healthz | python3 -c "import json,sys; d=json.load(sys.stdin); print([s for s in d['subsystems']['subsystems'] if s['name']=='object_storage'])"

    #  "detail":"bucket unreachable: Please enable R2 through the Cloudflare Dashboard.",
    #  "hint":"...reads fail over to the public bucket domain meanwhile, writes do not fail over at all.", ...}

This is already tracked and owner-gated: `prompts/RUN-ORDER.md` line 55, OWNER-ACTIONS row 36 ("Check Cloudflare's own R2 dashboard for the bucket behind `S3_BUCKET`... Flapping since 2026-09-08"). **This order does not touch R2 and does not attempt to fix the outage.** It closes a separate, code-fixable gap that is live right now and will recur on any future full-storage outage regardless of whether this one is R2-wide or just the signed-credential rot the fallback was originally built for (2026-09-07).

The gap: `api/cdn-object.js` already has a correct two-lane read path (signed R2 read, then `publicUrlOrNull(key)` streamed as a fallback when `isStorageInfrastructureError(err)` is true, lines 196-253). When R2 is disabled at the account level, BOTH lanes point at the same disabled product, so the fallback also throws, and the handler falls through to `return error(res, 502, 'upstream_error', 'failed to fetch object')` at line 254, a `cache-control: no-store` JSON body (`api/_lib/http.js:70`). The same two-lane-both-down path exists in `api/avatars/[id]/[action].js`'s `handleGlb` (lines ~707-742) for `/api/avatars/:id/glb`; that one is explicitly out of scope below.

Live confirmation, right now:

    # HTTP 502
    curl -s -o /dev/null -w "HTTP %{http_code}\n" "https://three.ws/api/avatars/d39c5db1-779c-47eb-9c8c-e30231519cf3/glb"

Blast radius, from the unauthenticated live-page sweep (`reports/page-audit-2026-10-24T20-43-27-109Z.md`, generated by `npm run audit:web`): this is not dozens of independent page bugs, it is one shared root cause rendering as a broken `<img>` icon on nearly every page that shows a thumbnail, forge preview, or avatar. `/rankings` alone logs 47 distinct `http-502` entries against `/cdn/thumb/*`, `/cdn/forge/*`, `/cdn/u/*` and `/api/avatars/*/glb`; `/monitor` logs 46 more against the same four path shapes plus a client-side `[agent-3d] boot failed` console-error when a GLB 502s. Same-day Cloud Run request logs confirm it server-side and at volume:

A root-cause trace (not a guess) confirmed the fallback itself is correctly wired and is not the bug: `publicUrl`/`publicUrlOrNull` (`api/_lib/r2.js` lines ~338-362) build `${env.S3_PUBLIC_DOMAIN}/${encodeR2Key(key)}`, and both `api/cdn-object.js` (line 196, streamed at 200-238) and `api/avatars/[id]/[action].js`'s `handleGlb` (line 707, streamed at 711-727) call it identically. Neither handler bypasses it. The gap is structural: there is no third lane for "the whole storage product is disabled," so the fallback fails the same way the primary did, and today the only thing left to do is answer `502 upstream_error`, `cache-control: no-store`. That `no-store` also means a page with 40 thumbnails re-hits the dead storage on every repeat view for as long as the outage lasts, with zero caching of the failure.

This is distinct from and not already covered by any open order: `401` (vitest), `403` (docs freshness), `433` (account_link_codes migration), `435` (sentiment-pulse LKG) and `436` (forge-finalize TTL reap) do not touch `cdn-object.js`, `r2.js`, or any image-serving path. It is also distinct from the R2-outage itself: the Cloudflare dashboard action in OWNER-ACTIONS row 36 is the fix for *why* storage is down; this order is the fix for *what the site shows users while it is*, which stays broken even after this specific outage clears, on the next one.
