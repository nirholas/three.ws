## Why this matters (measured 2026-10-25)

Every three.ws MCP server refuses a disabled tool call with a message that names a fix URL:

    curl -s -o /dev/null -w "%{http_code}\n" https://three.ws/settings/mcp-tools

returns 404 today. `find api -iname "*mcp-tools*"` finds only `api/_lib/viewer-mcp-tools.js` (an unrelated module: static tool definitions for the 3D-viewer MCP tools, not the tool-policy settings this order is about). `curl -s -o /dev/null -w "%{http_code}\n" https://three.ws/api/mcp-tools` also returns 404. `grep -rln "mcp_tool_settings" api/ src/` returns exactly two files: `api/_mcp/policy.js` (reads the table) and `api/_lib/migrations/20260922170000_mcp_tool_settings.sql` (creates it). There is no writer anywhere in the tree.

The backend this page needs already exists and is already wired to read from the table this order will start writing to:

- `packages/mcp-policy/src/runtime.js` line 23: `export const SETTINGS_URL = 'https://three.ws/settings/mcp-tools';`, quoted by `createPolicy()` in every `tool_disabled` refusal (line 145) across every hosted MCP server. `packages/mcp-policy/README.md` line 217 confirms: "quoted in every refusal." `api/_mcp-studio/dispatch.js` line 393 builds the same URL independently for the studio surface.
- `api/_mcp/policy.js`'s own header comment (lines 1-16, read today) already states the intended wiring in the present tense: "saved settings in `mcp_tool_settings` ..., written by `/settings/mcp-tools` through `/api/mcp-tools`" and the migration's own header comment (`20260922170000_mcp_tool_settings.sql`) says the same thing and documents the exact settings shape: `{ "groups": { "<group id>": true|false }, "tools": { "<tool name>": true|false } }`.
- `api/_mcp/policy.js` already exports `loadToolSettings(userId, apiKeyId)` (reads the account row and, if present, the per-key override row) and `invalidateToolSettings(userId)` (clears the 15-second in-memory memo on every instance after a write, so a save takes effect immediately rather than waiting out the memo). Both exist today and need no changes; the writer endpoint this order adds should call `invalidateToolSettings(user.id)` after every successful write.
- `packages/mcp-policy/src/groups.js` lines 59-86 already export `GROUPS`, a frozen array of `{ id, label, summary }` for all 26 tool groups ("in the order the settings page and the skill document list them", per its own doc comment, written before this page existed), e.g. `{ id: 'trading', label: 'Trading', summary: 'Quote and execute swaps from an agent wallet, copy trading, and signal subscriptions.' }` and `{ id: 'wallet', label: 'Wallet', summary: 'Agent wallets: balances, portfolio, provisioning, and transfers out.' }`. This is the exact data the settings page needs to render; do not invent a second copy of group labels.
- `packages/mcp-policy/src/enablement.js`'s `settingsToTokens()` (lines 112-122) is the function that actually consumes a saved row: it reads `settings.groups` and `settings.tools` only (confirmed: no `tiers` key is read from saved settings, even though the live spec grammar elsewhere supports tier tokens). This means the correct v1 settings UI is a per-group on/off list, not a per-tier toggle: turning a group on takes precedence over its tools' tiers (per `enablementFromTokens()`'s documented precedence, "tool over group over tier"), so switching on a group such as `trading` or `wallet` is what actually unlocks the financial-tier tools inside it. A UI that only exposed a "financial tier" master switch would not match what the saved-settings format is capable of expressing, and would require inventing a new settings shape the reader does not support. Build the per-group list; do not add a `tiers` key to what gets written.
- `docs/prompts/03-mcp-tool-policy-skill.md` line 9 already lists this exact gap as open, written before this order: "the `/settings/mcp-tools` page and the `/api/mcp-tools` writer for `mcp_tool_settings` (nothing writes the table yet...)."

Net effect today: every agent, connector, or MCP client that is refused a financial-tier tool (swaps, transfers, launches, domain registration, deletes; the tools gated by `tool_disabled`) is told to visit a page that cannot load and has no way to turn the tool on at all, short of an operator hand-editing the database or every caller individually discovering and using the `X-Three-Tools` header / `npx three-ws tools` CLI escape hatches (which exist but are not self-discoverable from the in-product refusal message itself). This is a live production gap affecting every disabled-tool refusal, documented as open in two places in this repository already, with its entire read path already shipped and only the write path and the page missing.

This is a new finding, not a duplicate: `grep -rln "mcp-tools\|mcp_tool_settings" prompts/finish/` before this order returns nothing in the `401`-`455` range. It is distinct from order 455 (`/settings/connections`, chat-gateway pairing, a different table and a different API) despite both being settings-page gaps discovered in the same sweep; do not merge them, they have no shared code path.
